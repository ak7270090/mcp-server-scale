The worker dies while the user is still thinking

ask_confirmation through the queue, 2 workers. The test kills the worker that asked, waits 1 s, then answers "yes".

A · the worker waits for the answer

MCP_ELICITATION_MODE=worker_waits
2×
user asked the question
5.6 s
until the answer
  1. Worker 1 asks, then blocks waiting.
  2. Worker 1 is killed; the answer has nobody to go to.
  3. 5 s without a heartbeat: JetStream redelivers the job.
  4. Worker 2 asks the user again.

B · the worker saves state and finishes

MCP_ELICITATION_MODE=continuation (default)
1×
user asked the question
1.7 s
until the answer
  1. Worker 1 returns the question plus saved state, and is done.
  2. Worker 1 is killed: nothing was waiting on it.
  3. The gateway queues the answer as a new job.
  4. Worker 2 finishes it.

Source: test_elicitation_under_failure.py (results/integration/elicitation-*.md). Variant B is the idea the 2026 MCP spec adopted as InputRequiredResult.
